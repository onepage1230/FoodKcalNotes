# Spec：記錄五項營養素與每日營養目標

- 狀態：已完成（2026-11-02）
- 決策依據：[ADR 0010](../decisions/0010-nutrients.md)；相關 ADR 0001、0002、0004、0005

## Problem Statement

飲食日誌目前只記錄熱量。使用者在減重期間也想知道每天吃了多少蛋白質、脂肪、碳水化合物、糖與鈉，例如確認蛋白質是否足夠、鈉是否超過建議上限，但 app 沒有這些數字，也沒有任何目標或提醒。

內附的食物資料、已累積的本機食物庫、網路搜尋與 AI 估算都只處理熱量，所以這不只是加欄位：大部分食物一開始就缺營養素資料，必須決定缺資料時怎麼補、怎麼標示，才不會讓不完整或估算的數字被當成精確值，也不會讓每一餐的 AI 呼叫次數失控。

## Solution

每項食物除了每 100g 熱量，再記錄每 100g 的蛋白質、脂肪、碳水化合物、糖（總糖）與鈉。程式依克數計算每項、每餐與每日的總量，與熱量的算法相同。

資料來源依序為：包裝營養標示、本機食物庫、網路搜尋（同一個被引用的來源）、AI 估算補缺。AI 估算的營養素在畫面上標「估」，並可帶著標記存進食物庫，之後遇到更可靠的來源就被覆蓋。熱量的取得與驗證規則完全不變。

減重計劃會依國健署標準帶出每日營養目標建議值（蛋白質下限、脂肪與碳水參考範圍、糖與鈉上限），使用者可逐項覆寫。首頁當日摘要顯示五項進度，只在有把握時提示不足或超標。

## User Stories

### 記錄與資料來源

1. As a 使用者, I want 拍一餐後自動得到每項食物的蛋白質、脂肪、碳水、糖與鈉, so that 我不用另外查營養素。
2. As a 使用者, I want 照片中包裝營養標示清楚時，五項營養素都直接依標示換算, so that 包裝食品的數字最準確。
3. As a 使用者, I want 營養標示只有每份數值時，依標示的每份重量換算成每 100g, so that 不同份量都能正確計算。
4. As a 使用者, I want 營養標示有部分欄位看不清楚時，只有那些欄位改用其他方式補, so that 看得清楚的數字不會被估算值取代。
5. As a 使用者, I want 本機食物庫命中時直接使用庫裡的營養素, so that 常吃的食物不必再呼叫 AI。
6. As a 使用者, I want 網路搜尋時同一次查詢就取得熱量和五項營養素, so that 不會因為加了營養素而多花一倍的搜尋額度。
7. As a 使用者, I want 營養素只有來自同一個被引用的來源時才算網路資料, so that 不會出現熱量和營養素來自不同網站卻都標成同一個出處的情況。
8. As a 使用者, I want 熱量的引用驗證規則維持不變, so that 加入營養素不會降低熱量的可信度。
9. As a 使用者, I want 來源缺少的營養素由 AI 估算補上, so that 每日總量盡量完整。
10. As a 使用者, I want AI 補估營養素時不能改動已經有來源的熱量, so that 熱量仍然以查得到的資料為準。
11. As a 使用者, I want 同一餐裡所有需要補估的項目合併成一次 AI 呼叫, so that 每餐最多只多一次呼叫。
12. As a 使用者, I want 熱量本身是 AI 估算時，同一次呼叫一併估五項營養素, so that 不會為營養素另外呼叫。
13. As a 使用者, I want AI 也估不出來的營養素記為「未知」而不是 0, so that 總量不會被低估卻看起來很精確。
14. As a 使用者, I want 每項食物仍保留一個主要來源標籤（營養標示／本機庫／網路資料／LLM 估算）, so that 我知道熱量從哪裡來。
15. As a 使用者, I want AI 估算的營養素在數字旁標「估」, so that 我分得出哪些數字有出處、哪些是估的。

### 食物庫

16. As a 使用者, I want 熱量有出處（網路資料或營養標示）的食物，連同估算的營養素和標記一起存進食物庫, so that 下次命中時不必再補估。
17. As a 使用者, I want 食物庫裡缺營養素的舊資料，在第一次命中時被補估並寫回, so that 食物庫越用越完整。
18. As a 使用者, I want 之後查到網路資料或營養標示時，覆蓋食物庫裡標記為估算的營養素, so that 估算值會逐漸被可靠資料取代。
19. As a 使用者, I want 食物庫裡的熱量和有出處的營養素永遠不被覆蓋, so that 已查證的資料不會被後來的結果改掉。
20. As a 使用者, I want 熱量是 AI 估算的食物仍然只在我按「AI 估算」並保存後才寫入食物庫, so that 既有的快取規則不變。
21. As a 使用者, I want 我手動改過名稱、熱量或營養素的項目不寫入食物庫, so that 我的個人調整不會污染共用資料。
22. As a 使用者, I want 朋友日誌的餐點預設仍不寫入食物庫，營養素也一樣, so that 共用庫的隔離規則不變。
23. As a 使用者, I want 食物庫畫面也顯示每 100g 的五項營養素與「估」標記, so that 我能查看庫裡的資料。

### 檢視與修改

24. As a 使用者, I want 結果頁每一項預設只顯示重量與熱量，營養素收合起來, so that 手機畫面不會太擠。
25. As a 使用者, I want 點開一項食物就看到它的五項營養素, so that 需要時能查看細節。
26. As a 使用者, I want 在結果頁修改某項食物的每 100g 營養素, so that 我能修正明顯不對的數字。
27. As a 使用者, I want 改過的營養素移除「估」標記, so that 畫面反映這是我確認過的數字。
28. As a 使用者, I want 改了克數後，營養素和熱量一起即時重算, so that 修正份量時不用重新分析。
29. As a 使用者, I want 結果頁顯示整餐的五項營養素總計, so that 我知道這一餐吃了什麼。
30. As a 使用者, I want 總計中有未知項目時顯示「至少 X g（N 項未知）」, so that 我知道總量可能偏低。
31. As a 使用者, I want 熱量和「蛋白質×4 + 碳水×4 + 脂肪×9」差距過大時看到提醒, so that 我能發現把每份當成每 100g 這類錯誤。
32. As a 使用者, I want 一致性提醒只是提醒，不擋下保存也不自動修改, so that 酒類、高纖食物等合理差異不會妨礙記錄。
33. As a 使用者, I want 「以新名稱重新查詢」單項時，營養素也一起重新取得, so that 改名後整項資料一致。
34. As a 使用者, I want 手動新增的食物可以只填熱量，營養素留空, so that 不設定 AI 也能照常記錄。

### 每日目標與提示

35. As a 使用者, I want 制定減重計劃時看到依國健署標準計算的每日營養目標建議值, so that 我不用自己查標準。
36. As a 使用者, I want 每個建議值都附上依據說明, so that 我知道這個數字從哪裡來。
37. As a 使用者, I want 蛋白質是每日下限目標, so that 攝取不足時會被提醒。
38. As a 使用者, I want 脂肪和碳水是參考範圍, so that 明顯偏離時會被提醒。
39. As a 使用者, I want 糖和鈉是每日上限, so that 超過時會被提醒。
40. As a 使用者, I want 逐項覆寫建議值, so that 我能依自己的情況（例如醫師建議）調整。
41. As a 使用者, I want 一鍵把某項恢復成建議值, so that 調整錯了可以還原。
42. As a 使用者, I want 體重或每日熱量目標改變時，沒覆寫的營養目標自動重算, so that 目標跟著計劃走。
43. As a 使用者, I want 覆寫過的目標在計劃改變時保持不動, so that 我的設定不會被蓋掉。
44. As a 使用者, I want 首頁當日摘要在熱量下方顯示五項營養素的進度, so that 一眼看到今天的狀況。
45. As a 使用者, I want 糖或鈉的已知總量已經超過上限時看到「超標」提示, so that 我能調整下一餐。
46. As a 使用者, I want 有未知項目但已知總量還沒超過上限時不顯示超標, so that 不會被誤報。
47. As a 使用者, I want 蛋白質未達下限且有未知項目時顯示「可能不足」, so that 提示的語氣反映不確定性。
48. As a 使用者, I want 糖的欄位標示為「總糖」並說明比對添加糖上限可能高估, so that 吃水果或喝牛奶的日子不會被誤導。
49. As a 使用者, I want 連勝仍然只看熱量, so that 營養素提示不會讓連勝變得幾乎無法維持。
50. As a 使用者, I want 功能上線前的餐點營養素顯示為未知，目標從上線當天起算, so that 舊紀錄不會造成錯誤提示。

### 資料與相容性

51. As a 使用者, I want 舊的餐點和食物庫在升級後照常顯示與編輯, so that 升級不會破壞既有資料。
52. As a 使用者, I want 匯出的 JSON 備份包含營養素欄位與估算標記, so that 備份是完整的。
53. As a 維護者, I want 內附的食藥署 137 筆資料包含五項營養素，數值取自原始資料集且不修改, so that 開箱就有可靠的營養素資料。
54. As a 維護者, I want 國健署資料若原本沒有營養素，就保留只有熱量，由補估機制處理, so that 不需要編造資料。
55. As a 維護者, I want `import-foods` 接受選填的五個營養素欄位，舊格式照常匯入, so that 我整理的資料可以逐步補上營養素。
56. As a 維護者, I want `import-foods --dry-run` 報告有多少筆含營養素, so that 匯入前能確認資料完整度。
57. As a 擁有者, I want 從手機記錄的餐點同樣取得營養素與提示, so that 手機與電腦體驗一致。
58. As a 擁有者, I want ChatGPT 與 Claude 備援時營養素的處理一致, so that 換服務不影響結果格式。

## Implementation Decisions

### 資料模型

- 每項食物新增五個選填欄位，全部是每 100g 可食部分：`proteinPer100g`（g）、`fatPer100g`（g）、`carbsPer100g`（g）、`sugarPer100g`（g，總糖）、`sodiumMgPer100g`（mg）。值為數字或 `null`；`null` 表示未知，不等於 0。
- 新增 `estimated`：字串陣列，列出哪些營養素欄位是 AI 估算的。只能包含上述五個欄位名稱。
- `source` 仍只代表熱量的來源，四種值與規則不變。
- 食物庫（`foods` 表的 JSON）與餐點快照（`meals.items` 的 JSON）都存這些欄位。**不改 SQL schema、不需要 migration**；缺欄位的舊資料讀出時視為 `null`。
- 驗證：食物驗證改為同時接受並保留五個營養素與 `estimated`（目前的白名單會丟棄未知欄位）。範圍檢查依每 100g 合理上限（例如三大營養素 0～100 g、鈉 0～40,000 mg），超出範圍視為無效。三大營養素加總超過 100 g 的情況視為無效。
- 每項、每餐、每日總量由程式以「克數 × 每100g ÷ 100」計算，與熱量相同；總計回傳「已知總量」與「未知項目數」，不把未知當 0。

### 分析流程

- **辨識呼叫**：辨識用的 JSON Schema，在每項食物原本的 `labelKcalPer100g` 之外，加入五個 `label…Per100g` 營養素欄位（可空）。提示詞要求依包裝營養標示換算，看不清楚填 `null`。
- **網路搜尋**：同一次呼叫要求回傳熱量與五項營養素，並要求營養素出自同一個來源。熱量的引用驗證是唯一門檻；驗證通過時，同一份回應中的營養素一併採用為網路資料；驗證失敗而降級為 LLM 估算時，回應中的營養素全部捨棄，改走估算。
- **估算呼叫**：估算用的 JSON Schema 加入五個營養素欄位；熱量走 LLM 估算時，同一次呼叫回傳五項，全部列入 `estimated`。
- **補估呼叫（新增）**：分析完成後，收集所有「熱量已有來源但有營養素為 `null`」的項目（營養標示、本機庫命中、網路資料），合併成一次結構化輸出呼叫，只要求回傳營養素，不回傳熱量；填入的欄位列入 `estimated`。沒有需要補估的項目時不呼叫。補估失敗時不讓整餐失敗，只保留 `null` 並加一則警告。
- 補估呼叫和其他呼叫一樣，經由既有的服務順序與備援、逾時重試機制。
- 「以新名稱重新查詢」單項、「AI 估算」單項，都套用同樣的營養素取得與補估流程。

### 快取（ADR 0010 的例外）

- 保存餐點時，既有的寫入條件不變（`cache` 旗標、非命中、來源屬於自動來源）。新寫入的食物連同營養素與 `estimated` 一起存。
- **新增：補值與覆蓋既有食物的營養素欄位**。條件與限制：
  - 只處理營養素欄位，不碰熱量、名稱、來源與其他欄位。
  - 庫裡為 `null` 的欄位：可被估算值或有出處的值補上。
  - 庫裡列在 `estimated` 的欄位：只能被有出處的值（網路資料、營養標示）覆蓋，覆蓋後從 `estimated` 移除；不能被另一個估算值覆蓋。
  - 庫裡有出處的欄位：永不覆蓋。
  - 使用者手動改過任何營養素或熱量的項目，不參與補值。
  - 朋友日誌在 `FRIENDS_CACHE` 關閉時不參與補值。
- 寫入時機仍只在保存餐點時；app 內仍不能直接編輯食物庫。

### 一致性檢查

- 由程式計算 `|熱量 − (蛋白質×4 + 碳水×4 + 脂肪×9)| ÷ 熱量`，三項都已知且熱量大於一個最低值時才檢查。門檻定案 25%、最低熱量 50 kcal/100g（食藥署資料驗證，見 ADR 0010）。
- 檢查結果只用於顯示提醒，不影響保存、快取與總計。

### 目標

- 減重計劃新增營養目標：每項分開存「覆寫值」（可空）；建議值不存，每次依目前計劃即時計算。實際目標 = 覆寫值 ?? 建議值。
- 建議值計算是純函式，輸入計劃（性別、年齡、身高、體重、活動量）與每日熱量目標，輸出五項目標及其類型（下限／範圍／上限）。公式與數字依國健署 DRIs 第八版與國民飲食指標，已查證並寫入 ADR 0010（蛋白質 1.1 g/kg、71 歲以上 1.2 g/kg；脂肪 20–30%、碳水 50–65% 熱量；糖 ≤ 熱量 10%；鈉 2,300 mg）。沒有計劃時蛋白質為 null。
- 糖上限依「添加糖 ≤ 每日熱量 10%」換算為公克。
- 當日狀態判斷也是純函式：輸入當日已知總量、未知項目數與目標，輸出每項的狀態（達標、不足、可能不足、超出範圍、超標、無法判斷）。規則：
  - 上限：已知總量 > 上限 → 超標；否則不提示（不論有無未知項目）。
  - 下限：已知總量 ≥ 下限 → 達標；未達且無未知 → 不足；未達且有未知 → 可能不足。
  - 範圍：低於範圍的判斷比照下限，高於範圍的判斷比照上限。
- 連勝的計算不變，只看熱量。
- 目標只套用在功能上線當天之後的日期；上線日期記在日誌的 meta。

### API 與前端

- 餐點、食物庫、當日摘要、匯出的回應都帶上營養素欄位、`estimated`、各層級總計（已知總量與未知數）。
- 設定 API 接受營養目標的覆寫值與清除覆寫。
- 結果頁每項的營養素區塊預設收合；修改營養素時，該欄位移出 `estimated`，整項標為使用者修改（比照修改熱量時改為 `manual` 且不快取的既有行為）。
- 首頁當日摘要在熱量下方加一列五項營養素的進度與提示；連勝區塊不變。
- 設定頁計劃區塊顯示建議目標、依據、覆寫與恢復；糖的欄位標示「總糖」與高估說明。

### 內附資料

- 食藥署 137 筆：從政府資料開放平台的原始資料集，依每筆 `notes` 中保留的樣品編號重新擷取五項營養素，數值不修改；`ATTRIBUTION.md` 的擷取說明同步更新。
- 國健署 22 筆：確認原始頁面有無營養素；沒有就維持只有熱量。
- 匯入腳本接受選填的營養素欄位與 `estimated`；dry-run 報告含營養素的筆數；既有的「名稱已存在就略過」規則不變（匯入不使用補值例外）。

## Testing Decisions

### 好的測試

- 只透過模組對外的介面測行為：給輸入，檢查輸出與可觀察的副作用（資料庫內容、HTTP 回應、模型被呼叫的次數與內容），不檢查內部函式或中間變數。
- 模型一律用假的 `infer`、`fetcher`、`anthropicFactory`，不打真實網路、不耗額度，沿用現有做法。
- 用 `:memory:` 或暫存資料夾的日誌，每個測試互相獨立。
- 中文測試名稱描述行為，例如「補估不改熱量；營養標示的值覆蓋食物庫中的估算值」。

### 測試層（seam）

1. **日誌模組**（以 `:memory:` 建立的日誌）
   - 營養素驗證：合法值、`null`、超出範圍、三大營養素加總超過 100 g。
   - 未知不等於 0：整餐與當日總計回傳已知總量與未知數。
   - 改克數時營養素重算。
   - 快取例外：`null` 被補值；估算值只被有出處的值覆蓋；有出處的欄位不被覆蓋；熱量永不被覆蓋；手動修改與朋友日誌不參與。
   - 舊格式的餐點與食物（沒有營養素欄位）照常讀取、編輯、匯出。
   - 匯出包含營養素與 `estimated`。
   - 參考：`food.test.js` 的「SQLite 跨日紀錄、熱量重算、編輯、重開與刪除」、「資料庫未命中時估算；確認前不寫入」。
2. **分析流程**（`analyzeMeal`、`lookupItem`，注入假的 `infer`）
   - 營養標示讀出五項；部分欄位為 `null` 時只補那些欄位。
   - 網路資料：引用驗證通過才採用同一回應中的營養素；降級時營養素全部改走估算。
   - 補估：同一餐多個缺值項目只呼叫一次；補估呼叫不包含熱量欄位，也不改動熱量；沒有缺值時不呼叫；補估失敗時整餐仍成功並附警告。
   - LLM 估算路徑一次回傳六個數值，並全部列入 `estimated`。
   - 參考：「照片營養標示直接使用，不查熱量」、「真實搜尋引用才標記為 web；虛構引用退回估算」、「未收錄項目最多 3 項同時查詢」。
3. **HTTP API**（`createApp`，搭配假的服務）
   - 只放一到兩個端對端情境：背景分析自動存檔後，餐點與食物庫中的營養素和 `estimated` 正確；朋友日誌在 `FRIENDS_CACHE` 關閉時不寫入也不補值。
   - ChatGPT 與 Claude 的結構化輸出都帶上新的營養素欄位。
   - 參考：`app.test.js` 的「背景分析自動存成餐點：LLM 估算不寫入共用食物庫…」、「ChatGPT：辨識與估算帶 strict text.format」。
4. **前端純函式**（與 `planGoal` 同一個模組）
   - 建議目標值的計算（第三階段查證後的公式）。
   - 覆寫與恢復：覆寫值優先；計劃改變時只有未覆寫的項目跟著變。
   - 當日狀態判斷：上限、下限、範圍三種類型 × 有無未知項目的所有組合。
   - 一致性檢查：門檻內外、缺任一營養素時不檢查。
   - 參考：`plan.test.js`。

### 不寫自動測試的部分

- 畫面排版、收合互動：手動在手機與電腦上確認。
- 食藥署資料的重新擷取：一次性的維護作業，以 `import-foods --dry-run` 與人工抽查驗證。

## Out of Scope

- 營養素的每週統計與圖表。
- 推播通知或任何畫面以外的提醒。
- 管理員檢視顯示營養素。
- 五項以外的營養素（膳食纖維、飽和脂肪、反式脂肪、膽固醇等）。
- 舊餐點的營養素批次補算。
- 把營養素納入連勝。
- 添加糖的獨立記錄。
- app 內編輯食物庫。

## Further Notes

### 交付階段

每一階段都可單獨使用、測試與 commit，依序進行：

1. **資料層**：資料模型與驗證、快取例外、分析流程（營養標示、網路、估算、補估）、匯入與匯出、內附資料重新擷取。完成後資料開始累積，即使還沒有畫面。
2. **顯示**：結果頁的收合與修改、整餐總計、首頁摘要的營養素列（先不含目標）、食物庫畫面、一致性提醒（門檻在此階段驗證）。
3. **目標**：查證國健署標準並寫入 ADR 0010、建議值計算、覆寫與恢復、當日狀態判斷與提示。
