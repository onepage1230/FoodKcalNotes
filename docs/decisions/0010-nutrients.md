# 0010 加入五項營養素，以及估算營養素的快取例外

- 狀態：已採用（分三階段實作）

## 背景

目前每項食物只有一個數值：`kcalPer100g`。想同時記錄蛋白質、脂肪、碳水化合物、糖與鈉，並設定每日目標與超標提示。

問題不在儲存：`foods.data` 與 `meals.items` 都是 JSON 欄位，加欄位不需要改 schema。難的是**資料不完整**：

- 內附的食藥署資料只擷取了熱量（原始資料集其實有這五項）；國健署「熱量知多少」可能只有熱量。
- 已存進食物庫的網路資料只有熱量。
- 網路來源常常只寫熱量，或只寫部分營養素。

若照 [0004](0004-food-library-caching.md) 的規則，LLM 估算一律不寫入食物庫、先存的資料不覆蓋，那麼「熱量有出處、營養素要靠估算」的食物，每次命中都得重新估算營養素，違反 [0005](0005-tiered-ai-calls.md) 命中食物庫就不呼叫模型的設計；或者營養素永遠是空的。

## 考慮過的選項

**A. 營養素和熱量用同一套規則**：只有可查證的來源才存，缺的就是未知。
- 優點：規則單純，庫裡每個數字都有出處。
- 缺點：大部分食物的營養素會長期是空的，目標與提示形同虛設。

**B. 每個營養素各自記錄完整的來源與引用**
- 優點：最完整、最透明。
- 缺點：資料結構與 UI 都複雜數倍；手機畫面放不下。

**C. 一個主來源加上「估算欄位清單」，估算的營養素可以帶標記寫入食物庫（採用）**
- 優點：資料很快就完整；命中後不再呼叫模型；使用者仍看得出哪些數字是估的。
- 缺點：庫裡會有估算值；要多一條「估算欄位可被覆蓋」的例外。

## 決定

採用 C。

### 欄位

固定五項，全部是每 100g 可食部分，可為 `null`（未知，不等於 0）：

| 欄位 | 單位 |
| --- | --- |
| `proteinPer100g` | g |
| `fatPer100g` | g |
| `carbsPer100g` | g |
| `sugarPer100g` | g（總糖，含天然糖） |
| `sodiumMgPer100g` | mg |

另加 `estimated`：列出哪些營養素欄位是 AI 估算的，例如 `["sugarPer100g", "sodiumMgPer100g"]`。`source` 仍代表**熱量**的來源，規則不變。

熱量仍然必填，且仍由程式計算（[0001](0001-kcal-computed-by-program.md)）；營養素總量同樣是「克數 × 每100g ÷ 100」，由程式計算。

### 取得順序

1. **包裝營養標示**：辨識那次呼叫一併讀五項（台灣法規要求標示），換算方式同熱量。看不清楚的欄位填 `null`，交給第 4 步。
2. **本機食物庫**：直接使用；缺的營養素交給第 4 步。
3. **網路搜尋**：同一次呼叫查六個數值，不增加呼叫次數。熱量的引用核對（[0002](0002-citation-verification.md)）仍是唯一門檻；其他營養素必須來自**同一個被引用的來源**才算網路資料。不為了補營養素做第二次搜尋。
4. **AI 估算補缺**：仍為 `null` 的營養素由模型估算並列入 `estimated`。熱量已有來源時，**模型不能改動熱量**。同一餐所有需要補估的項目合併成一次呼叫。熱量本身走 LLM 估算時，同一次呼叫一併估五項。
5. 真的估不出來才保留 `null`。

### 快取例外（相對於 0004）

1. 熱量來源可自動寫入（`web`、`label`）的項目，連同估算的營養素與 `estimated` 標記一起寫入。
2. 已在庫裡的食物，若某營養素是 `null` 或列在 `estimated` 中，**可以被補上或覆蓋**：
   - 估算值可以補 `null`；
   - 網路資料或營養標示的值可以覆蓋估算值，並從 `estimated` 移除。
3. 其餘 0004 規則不變：熱量與非估算欄位永不覆蓋；熱量是 LLM 估算的項目仍只有使用者按「AI 估算」並保存才寫入；使用者改過名稱、熱量或營養素的項目不寫入。
4. 寫入時機仍只在保存餐點時（`saveMeal()`），app 內仍不能直接編輯食物庫。

### 一致性檢查

熱量與「蛋白質×4 + 碳水×4 + 脂肪×9」差距超過門檻時，結果頁提醒，不擋下、不修正。用來抓「把每份當成每 100g」這類量級錯誤。

**門檻定案：25%；熱量低於 50 kcal/100g 不檢查。** 以食藥署 137 筆驗證（三大營養素都已知者 132 筆）：

- 差距 `|kcal − 換算| ÷ kcal`：最小 0%、中位數 2.3%、P90 16.6%、P95 19.2%、P99 29.5%、最大 45%。
- 差距最大的是低熱量食物：美式咖啡（2 kcal，45%）、芭樂（34 kcal，31%）、綠竹筍（22 kcal，30%）、番茄（21%）、綠奇異果（21%）。原因是換算結果偏高：這些食物的碳水含大量膳食纖維（約 2 kcal/g，非 4），低熱量時相對誤差又被放大。
- 酒精（7 kcal/g）會讓換算偏低，糖醇也會；資料集中沒有這類食物出現在前段，但保留不提醒、不修正的設計以免誤擋。
- 套用最低熱量 50 後檢查 101 筆，差距 P50 1.8%、P90 12.2%、P95 14.8%、P99 19.1%、最大 21.3%（綠奇異果），**25% 門檻下觸發 0 筆**。最低值取 50：30 以下仍會誤報 1 筆（芭樂），20 到 49 之間的水果、茶與清湯都是纖維或四捨五入造成的誤差。
- 門檻 25% 高於實測最大值 21.3% 留有餘裕；把每份當成每 100g 的錯誤通常差距在數倍以上，25% 足以抓到。更低（15%）會觸發 19 至 22 筆誤報。
- 取捨：熱量低於 50 kcal/100g 的食物（飲料、蔬菜、清湯）即使錯了也不提醒；高纖、含酒精的食物若落在邊緣仍可能提醒，因此只是提醒。
- 實作：`client/nutrients.js` 的 `kcalMismatch`；數值檢查寫在 `tests/nutrient-consistency.test.js`，會讀食藥署資料斷言觸發筆數。

### 目標與提示

- 建議值依衛福部國健署「國人膳食營養素參考攝取量（DRIs）」與國民飲食指標，由計劃的體重、年齡與每日熱量目標推算（`client/nutrient-goals.js` 的 `suggestedGoals`，純函式）。公式與出處見下方「建議值的公式與出處」。
- 類型：蛋白質為下限；脂肪、碳水為參考範圍；糖、鈉為上限。糖以「添加糖 ≤ 總熱量 10%」換算上限，但記錄的是總糖，UI 須說明可能高估。
- 每項可覆寫；建議值與覆寫值分開存，未覆寫的項目隨計劃自動重算。
- 有未知值時，只在有把握時提示：已知值已超過上限才算超標；下限未達且有未知項目時顯示「可能不足」。
- 連勝仍只看熱量。

#### 建議值的公式與出處（查證日期 2026-11-02）

| 項目 | 類型 | 公式 | 依據 |
| --- | --- | --- | --- |
| 蛋白質 | 下限 | （減重計劃進行中已由 [ADR 0012](0012-protein-floor-during-deficit.md) 取代）目前體重 × 1.1 g/kg（71 歲以上 × 1.2 g/kg），四捨五入到整數 g | DRIs 第八版蛋白質 RDA |
| 脂肪 | 範圍 | 每日熱量 × 20%～30% ÷ 9 kcal/g | DRIs 第八版脂質 AMDR（4 歲以上 20–30%） |
| 碳水化合物 | 範圍 | 每日熱量 × 50%～65% ÷ 4 kcal/g | DRIs 第八版碳水化合物 AMDR（1 歲以上 50–65%） |
| 糖（總糖） | 上限 | 每日熱量 × 10% ÷ 4 kcal/g | 國民飲食指標：添加糖不宜超過總熱量 10% |
| 鈉 | 上限 | 固定 2,300 mg | DRIs 第八版鈉 CDRR（13 歲以上 2,300 mg） |

「每日熱量」是使用者的每日熱量目標（`goal`），不是 TDEE；減重時目標較低，脂肪、碳水、糖的克數也跟著變少。

  - 蛋白質章節（書頁 117）：「第八版之蛋白質建議量為成人 1.1 g/kg BW，70 歲以上老人與 80 歲以上老老人 1.2 g/kg BW」，再以參考體重（男 58–64、女 50–52 kg）換算成總表的男 70 g/d、女 60 g/d。總表的年齡分層是「51–70 歲」與「71 歲－」（足歲），所以程式以 **71 歲以上** 用 1.2 g/kg。
  - 蛋白質章節（書頁 122）：「以低熱量飲食減重時蛋白質之熱量百分比應該要提高」，但**沒有給出減重期間的數字**，所以不另加減重係數；改用 g/kg 計算本身就讓蛋白質不隨熱量目標下降。
  - 總表（書頁 718–722）：碳水化合物 AMDR 50–65%（RDA 130 g）；脂質 AMDR 20–30%；鈉 CDRR 2,300 mg（13 歲以上；CDRR = 慢性疾病風險降低攝取量）。

- 版本差異：
  - 鈉：較早的衛生署／國民飲食指標寫「每日鈉攝取量不超過 2,400 mg（鹽 6 g）」（例如國健署〈[正確飲食習慣](https://www.hpa.gov.tw/Pages/Detail.aspx?nodeid=543&pid=8365&sid=8382)〉，僅經搜尋摘要確認）；DRIs 第八版改為 CDRR 2,300 mg。採用較新、較嚴的 **2,300 mg**。
  - 第九版 DRIs 草案（[國健署 2026-03-02 預告](https://www.hpa.gov.tw/Pages/Detail.aspx?nodeid=129&pid=19883)；增修訂說明附件從[彰化縣衛生局轉載 PDF](https://dep.hcchb.gov.tw/uploaddowndoc?file=announcement%2F202603091453230.pdf&filedisplay=%E9%99%84%E4%BB%B61-%E7%AC%AC%E4%B9%9D%E7%89%88%E3%80%8C%E5%9C%8B%E4%BA%BA%E8%86%B3%E9%A3%9F%E7%87%9F%E9%A4%8A%E7%B4%A0%E5%8F%83%E8%80%83%E6%94%9D%E5%8F%96%E9%87%8F%E3%80%8D%E5%90%84%E7%AB%A0%E7%AF%80%E5%A2%9E%E4%BF%AE%E8%A8%82%E8%AA%AA%E6%98%8E%28%E5%A5%89%E6%A0%B8%29.pdf&flag=doc)閱讀）：成人蛋白質維持 1.1 g/kg，但 1.2 g/kg 改從 **65 歲**起；脂質 20–30%、碳水 50–65% 不變；成人鈉 CDRR 改寫為「< 2,300 mg」。查證時找不到正式公告，所以仍用第八版；第九版正式公告後把蛋白質的年齡門檻改為 65 歲。

#### 計算與儲存的決定

- **沒有減重計劃時**：蛋白質建議值為 `null`（UI 顯示「—」並提示設定計劃），不用總表的男 70／女 60 g 代替，因為那需要性別，而且以參考體重換算，與使用者體重可能差很多；脂肪、碳水、糖照每日熱量目標計算，鈉是固定值。
- **用目前體重**（最新一筆體重紀錄，沒有紀錄時才用計劃的 `weight`；減重進行中的下限改依 [ADR 0012](0012-protein-floor-during-deficit.md)），不用目標體重或理想體重：DRIs 以實際體重（BW）表示。體重較重的人下限會比總表高，作為減重期間的下限可以接受（上方蛋白質章節也建議減重時提高比例）。
- 克數四捨五入到整數；覆寫值接受小數。
- **設定只存覆寫值**：`settings.nutrientGoals`，形如 `{ "protein": { "min": 80 }, "fat": { "min": 40, "max": 60 } }`，缺的項目沿用建議值；建議值不存。覆寫以整項為單位（範圍的上下限一起覆寫）。API 以 patch 合併，單項傳 `null` 恢復建議值，整個傳 `null` 全部恢復。驗證：只能是五項之一、欄位必須符合類型、數字在合理範圍（g 類 1～500，碳水 1～1,500，鈉 100～10,000 mg）、範圍的下限 ≤ 上限。清除減重計劃不會清除覆寫。

### 相容性

- 舊餐點不補算，營養素視為未知；目標從功能上線當天起算。
- `data/*.json`、`import-foods`、匯出備份加上選填的五個欄位，舊格式照常匯入。
- 食藥署 137 筆從原始資料集重新擷取，數值不修改。

## 取捨

- **庫裡會有估算值**：雖有標記，但命中後不再查證，估錯的營養素會一直沿用，直到遇到網路資料或營養標示覆蓋。
- **熱量與營養素可信度不一**：一項食物的熱量可能有出處、糖與鈉卻是估的；UI 必須在數字旁標「估」，否則會誤導。
- **每餐可能多一次呼叫**：命中但缺營養素的項目第一次要補估；之後隨著補齊而減少。
- **總糖比添加糖上限**：常吃水果、喝牛奶的日子容易誤報。
- **只有一個主來源**：網路來源缺的營養素改為估算時，無法顯示該營養素自己的出處。

## 何時重新評估

- 估算的營養素明顯偏差、使用者常手動修正 → 改為估算值不寫入食物庫，或需使用者確認。
- 一致性檢查經常誤報或漏報 → 調整門檻，或改成依食物類別（飲料、酒類、高纖食物）分別處理。
- 需要更多營養素（膳食纖維、飽和脂肪等）→ 照同一模式加欄位；若超過十項，再考慮改成可擴充的清單。
- 能可靠取得添加糖資料 → 改以添加糖比對上限。
